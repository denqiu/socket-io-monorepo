<h2 id="custom-rules">Custom Rules (See <a href="https://eslint.org/docs/latest/extend/custom-rules">link</a> for more information)</h2>

In the example custom ESLint rule file [enforce-foo-bar.js](https://github.com/eslint/eslint/blob/main/docs/_examples/custom-rule-tutorial-code/enforce-foo-bar.js), several key properties are defined within the custom rule. Here's a breakdown of these properties and their potential options:

---

<h3 id="rules-meta-property"><b>1. <code>meta</code></b></h3>
The `meta` property contains metadata about the rule and serves as a description for ESLint to interpret how the rule works.

#### **Key Properties of `meta`:**

- **`type`**: Specifies the category of the rule.
  - Options:
    - `"problem"`: Indicates the rule addresses code errors.
    - `"suggestion"`: Provides recommendations to improve code quality.
    - `"layout"`: Enforces consistent code style.

- **`docs`**: An object providing documentation details for the rule.
  - **`description`**: A short description of the rule.
  - **`recommended`**: A boolean indicating if the rule is part of the recommended ruleset.
  - **`url`**: A URL to the rule's documentation.

- **`fixable`**: Indicates whether ESLint can automatically fix violations.
  - Options:
    - `"code"`: Automatically fixes issues within the code.
    - `"whitespace"`: Automatically fixes spacing and formatting issues.

- **`schema`**: Defines the structure of options the rule accepts.
  - This is an array of JSON schema objects. Each object describes a single option, including its type, default value, and constraints.

- **`messages`**: Stores user-friendly error messages for different rule violations.
  - Example:
    ```javascript
    messages: {
        fooBarViolation: "Avoid using foo and bar together."
    }
    ```

---

<h3 id="rules-create-function"><b>2. <code>create</code></b></h3>

This function defines the core logic of the rule. It describes how ESLint detects violations and optionally provides fixes.

- **See <a href="https://eslint.org/docs/latest/extend/custom-rules#the-context-object">link</a> for more information about `context` argument.**
- **See <a href="#rule-listener-selectors">here</a> for more information about rule listener selectors such as `Identifier`. Update: Finally found docs. See <a href="https://eslint.org/docs/latest/extend/custom-rules#scope-types">link</a>.**

#### **Parameters of `create`:**
- **`context`**: An object representing the linting environment. Key methods include:
  - **`report`**: Reports rule violations.
    - Properties for `report`:
      - `node`: The AST node where the issue is found.
      - `messageId`: The ID of a message defined in `meta.messages`.
      - `fix`: A function describing how to automatically fix the problem.

#### **Example Usage:**
```javascript
create(context) {
  return {
    Identifier(node) {
      if (node.name === "foo") {
        context.report({
          node,
          messageId: "fooBarViolation",
        });
      }
    }
  };
}
```

In this example, the rule triggers a report when an identifier named "foo" is encountered.

---

<h3 id="rules-schema-in-depth"><b>3. <code>schema</code> in Depth</b></h3>
The `schema` property is crucial for validating the rule's options.

**See <a href="#explain-schema">here</a> for more information.**

#### **Example Structure:**
```javascript
schema: [
  {
    type: "object",
    properties: {
      allowFoo: {
        type: "boolean",
        default: false
      }
    },
    additionalProperties: false
  }
]
```

#### **Key Options for `schema`:**
- **`type`**: The data type of the option.
  - `"string"`, `"boolean"`, `"number"`, or `"object"`.
- **`properties`**: Defines specific fields for an object type.
- **`additionalProperties`**: If `false`, disallows properties not explicitly defined in `properties`.

---

<h3 id="rules-fix-function"><b>4. <code>fix</code></b></h3>
If the rule is fixable, a `fix` function can be included within the `report` call.

#### **Structure:**
```javascript
fix: function (fixer) {
  return fixer.replaceText(node, "correctCode");
}
```

#### **Fixer Methods:**
- **`replaceText(node, text)`**: Replaces the text of a node with the given text.
- **`insertTextAfter(node, text)`**: Inserts text after the specified node.
- **`removeRange(range)`**: Removes a range of text.

---

### Example Workflow:
When ESLint encounters a rule violation:
1. **AST Analysis**: ESLint's parser analyzes the code into an Abstract Syntax Tree (AST).
2. **Rule Execution**: The `create` function inspects the AST based on logic provided.
3. **Error Reporting**: Violations are reported using `context.report`.
4. **Fix Application (Optional)**: If `fixable`, ESLint applies fixes based on the `fix` logic.

This structure allows the rule to integrate seamlessly with ESLint and provides flexibility for customization. For further reference, visit the [source file](https://github.com/eslint/eslint/blob/main/docs/_examples/custom-rule-tutorial-code/enforce-foo-bar.js).

<h3 id="invalid-test-cases"><b>3. Properties for Invalid Test Cases</b></h3>

For `invalid` test cases, additional properties are required to specify the expected errors.

#### **`errors`**
- **Description**: An array of expected errors triggered by the rule.
- **Type**: Array of objects
- **Properties**:
  - **`message`**: The error message (or part of it) expected from the rule.
    ```javascript
    { message: "Avoid using foo and bar together." }
    ```

  - **`messageId`**: References a specific `messageId` in the rule's `meta.messages`.

    ```javascript

    ```
  - **`line` and `column`**: Specifies the exact location of the error.
    ```javascript
    { line: 2, column: 5 }
    ```

#### **`output`**
- **Description**: The expected fixed code after applying the rule's fix logic.
- **Type**: String
- **Example**:
  ```javascript

  ```

<h3 id="test-case-example"><b>4. Complete Test Case Example</b></h3>
Below is a detailed test case for a rule that disallows `foo` and `bar` being used together in the same file:

```javascript
const { RuleTester } = require("eslint");
const rule = require("./no-foo-bar"); // Import your custom rule

const ruleTester = new RuleTester({
  parserOptions: { ecmaVersion: 2021, sourceType: "module" }
});

ruleTester.run("no-foo-bar", rule, {
  valid: [
    {
      code: "let foo = 42;", // Valid: Only 'foo' is used
      options: [{ allowFoo: true }], // Rule option allowing 'foo'
      filename: "/path/to/test/fooFile.js", // File context for testing
      settings: { environment: "node" } // Global settings for the rule
    },
    {
      code: `
        const bar = "Hello";
        export default bar;
      `, // Valid: Only 'bar' is used
      filename: "/path/to/test/barFile.js" // Associated filename
    }
  ],
  invalid: [
    {
      code: `
        let foo = 42;
        let bar = 13;
        console.log(foo, bar);
      `, // Invalid: Both 'foo' and 'bar' used
      filename: "/path/to/test/fooBarFile.js", // File where the error occurs
      options: [{ allowFoo: false }], // Rule configuration: 'foo' not allowed with 'bar'
      settings: { environment: "node" }, // Node environment
      errors: [
        { messageId: "fooBarConflict", line: 2, column: 13 }, // 'foo' error
        { messageId: "fooBarConflict", line: 3, column: 13 }  // 'bar' error
      ],
      output: `
        let foo = 42;
        // let bar = 13; (Removed as a fix)
        console.log(foo);
      ` // Fixed version of the code
    }
  ]
});
```

---

### **Key Takeaways**
- The `code` property is required for all test cases.
- `filename`, `options`, and `settings` provide additional context for testing.
- Invalid test cases use `errors` to define expected violations and optionally `output` for fix validation.

For further details, check the [ESLint documentation](https://eslint.org/docs/latest/integrate/nodejs-api#ruletester).

### **Understanding Rule Listener Base Selectors**

In ESLint, **Rule Listener Base Selectors** (or simply **selectors**) are keys in the `create` function's object that map to specific types of nodes in the **Abstract Syntax Tree (AST)**. These selectors allow a rule to "listen" for particular nodes (like `Identifier`, `Literal`, `FunctionDeclaration`, etc.) and define actions to perform when such nodes are encountered.

### **1. What Are AST Nodes?**
AST nodes represent parts of the source code. For example:
- `Identifier`: Represents variable or function names.
- `Literal`: Represents fixed values like numbers, strings, or booleans.
- `FunctionDeclaration`: Represents function declarations.

By targeting specific selectors, a rule can focus on analyzing or transforming only relevant parts of the code.

---

### **2. Common Rule Listener Selectors**
Below is a list of commonly used selectors in ESLint with explanations and examples:

#### **a) `Identifier`**
- **Description**: Matches variable or function names.

- **Example**:
  ```typescript

    type: "problem",
    docs: {
      description: "Disallow certain bad practices.",
      recommended: true
    },
    messages: {
      noEval: "Avoid using 'eval'.",
      noVar: "Use 'let' or 'const' instead of 'var'.",
      strictEquality: "Use '===' instead of '=='."
    }
  },
  create(context) {
    return {
      CallExpression(node: TSESTree.CallExpression) {

          context.report({ node, messageId: "noEval" });
        }
      },
      VariableDeclaration(node: TSESTree.VariableDeclaration) {
        if (node.kind === "var") {
          context.report({ node, messageId: "noVar" });
        }
      },
      BinaryExpression(node: TSESTree.BinaryExpression) {
        if (node.operator === "==") {
          context.report({ node, messageId: "strictEquality" });
        }
      }
    };
  }
};
```

### **When `schema` is Defined**
When the `schema` property is present, it provides validation for the options passed in the ESLint configuration. The rule verifies that the provided options match the expected structure before running. If the options are invalid, ESLint throws an error during configuration parsing.

#### **Rule with `schema`**
```javascript

  meta: {
    type: "suggestion",
    docs: {
      description: "Disallow specified variable names.",
      recommended: false,
    },
    schema: [
      {
        type: "object",
        properties: {
          disallowedNames: {
            type: "array",
            items: { type: "string" },
            default: []
          }
        },
        additionalProperties: false
      }
    ],
    messages: {
      disallowedName: "The variable '{{ name }}' is disallowed."
    }
  },
  create(context) {
    const { disallowedNames = [] } = context.options[0] || {};

    return {
      Identifier(node) {
        if (disallowedNames.includes(node.name)) {
          context.report({
            node,
            messageId: "disallowedName",
            data: { name: node.name }
          });
        }
      }
    };
  }
};
```

#### **Behavior**
1. **Valid Options**:

     ```javascript
     }
     ```

2. **Invalid Options**:
   - ESLint throws a configuration error before the rule runs:
     ```bash
     Error: Rule custom-rule received invalid options:
     - "disallowedNames" must be an array of strings.
     ```
